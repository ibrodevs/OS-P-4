## Обоснование выбора окружения

Для работы используется Python 3, потому что он предоставляет стандартные модули `threading`, `multiprocessing` и `concurrent.futures`, позволяющие на одном языке сравнить потоки и процессы. Эксперименты ориентированы на CPython, где существует GIL, поэтому результаты хорошо показывают различие между CPU-bound и I/O-bound задачами.

## Выполнение задания

### 1. CPU-bound задача

`cpu_benchmark.py` сравнивает три варианта суммирования чисел:

1. обычное последовательное выполнение;
2. четыре `threading.Thread`;
3. четыре процесса `multiprocessing`.

Каждый вариант выполняется несколько раз, а для сравнения используется медианное время. Все варианты должны получить одинаковую итоговую сумму.

### 2. Почему потоки не ускоряют CPU-bound код

В обычном CPython действует **GIL — Global Interpreter Lock**. В рамках одного процесса Python-байткод в конкретный момент исполняет только один поток.

Поэтому при вычислительной задаче четыре Python-потока не превращаются автоматически в четыре параллельно работающих ядра. Они переключаются между собой и дополнительно несут накладные расходы на планирование.

### 3. Почему процессы могут ускорить CPU-bound задачу

Каждый процесс имеет собственный интерпретатор Python и собственный GIL. Поэтому несколько процессов действительно могут выполнять вычисления на разных ядрах процессора параллельно.

При этом процессы дороже потоков:

- нужно создавать отдельные процессы;
- у каждого отдельное адресное пространство;
- требуется межпроцессный обмен данными;
- на малом объёме работы накладные расходы могут оказаться больше выигрыша.

### 4. I/O-bound задача

`network_benchmark.py` сравнивает загрузку 20 URL:

1. последовательно;
2. через `ThreadPoolExecutor(max_workers=4)`;
3. через `ProcessPoolExecutor(max_workers=4)`.

В сетевой задаче большая часть времени проходит в ожидании ответа от удалённого сервера. Во время блокирующего I/O поток не занят вычислением Python-байткода, поэтому другие потоки могут работать.

Именно поэтому потоки обычно особенно эффективны для I/O-bound задач.

### 5. Общая и изолированная память

`memory_demo.py` изменяет глобальный список сначала из потока, затем из дочернего процесса.

Для потока изменение видно родителю, потому что потоки одного процесса используют одно адресное пространство.

Для дочернего процесса обычное изменение глобального списка не меняет список родителя: процессы имеют логически изолированную память.

Принципиальная схема результата:

```text
Thread:
Parent before: [1, 2, 3]
Thread:        [1, 2, 3, 4]
Parent after:  [1, 2, 3, 4]

Process:
Parent before: [1, 2, 3]
Process:       [1, 2, 3, 5]
Parent after:  [1, 2, 3]
```

## Ключевые результаты

- CPU-bound задача сравнивается в трёх вариантах;
- потоки в CPython не дают ожидаемого ускорения вычислительного Python-кода из-за GIL;
- процессы могут использовать несколько CPU-ядер;
- в I/O-bound задаче потоки позволяют перекрывать периоды ожидания;
- потоки разделяют память процесса;
- процессы имеют отдельные адресные пространства.

---

## Вывод

Потоки и процессы решают разные задачи. Потоки лёгкие и хорошо подходят для конкурентного I/O, но в CPython ограничены GIL для CPU-bound Python-кода. Процессы дороже, зато позволяют реальное параллельное выполнение вычислений на нескольких ядрах. Кроме того, потоки используют общую память, тогда как процессы изолированы и требуют специальных механизмов для обмена данными.
